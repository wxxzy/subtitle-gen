# subgen —— 视频/音频自动生成字幕

本地运行，不上传任何文件。基于 **faster-whisper**（CTranslate2 后端）+ **ffmpeg**，
  
支持 GPU 加速、词级时间戳、智能断句，一次可导出 SRT / VTT / ASS / LRC / TXT。

## 二、它是怎么做出来的

```
视频文件
   │
   ├─[ffmpeg]─> 16 kHz 单声道 WAV        （Whisper 的原生输入规格，省掉内部重采样）
   │
   ├─[VAD]────> 切掉静音段               （提速 20~40%，同时大幅减少"幻听"）
   │
   ├─[faster-whisper]─> 词级时间戳 token 流
   │                    停顿/标点/长度三重启发式
   ├─[segmenter]──────> 字幕行（自动折行、控制时长）
   │
   ├─[translator]─────> 译文（可选，双语时原文保留）   ← 离线 / LLM 双后端
   │
   └─[formats]─> .srt / .vtt / .ass / .lrc / .txt
```

**为什么用 faster-whisper 而不是原版 Whisper？**
  
同样是 OpenAI 的模型权重，但换了 CTranslate2 推理引擎：速度提升 4~~8 倍，显存占用降低一半，
  
精度完全一致。原版 Whisper 在 1080 Ti 上跑 large-v3 大约 3~~4 倍实时，这套方案能到 15 倍以上。

## 三、字幕翻译（中 → 英 / 日 / 韩 ……）

字幕翻译和普通文本翻译不是一回事：**时间轴必须原样保留**，译文长度会膨胀（中译英约 1.5~2 倍）
  
需要重新折行，还常要出双语。这些都已内置处理。

### 3.0 先想清楚：分开还是合并？

这是用之前最该决定的事。**两者不是对立的，而是不同层面的事**：

| 需求                        | 该怎么做                  | 理由                  |
| ------------------------- | --------------------- | ------------------- |
| 上传 B站 / YouTube / Netflix | **分开**各一份文件           | 平台要独立语言文件，做成多轨供观众自选 |
| 分发给不同国家的观众                | **分开**                | 各自只下自己那份，体积小        |
| 单独校对某一语言                  | **分开**                | 改英文不动中文，对轴互不干扰      |
| 一个文件里能切语言                 | **多轨封装**（`--mux`）     | 只传一个文件，播放器菜单里切      |
| 抖音 / 小红书 / 视频号            | **合并烧录**（`--burn`）    | 平台不支持多轨，只能烧进画面      |
| 学外语 / 双语对照                | **合并**（`--bilingual`） | 同屏对照才有意义            |

一条经验：**字幕文件的规范形态是「每种语言一条独立轨道」**，合并只发生在
  
播放或烧录的那一刻。所以本工具默认**输出各语言独立文件**，
  
需要合并时用 `--bilingual`（同屏）或 `--mux`（多轨）——这三种可以同时要。

```bash
# 默认：中文、英文各一份（都能单独用）
subgen.bat 视频.mp4 -t en
#   → 视频.zh.srt   视频.en.srt

# 再加一份双语（用于自己看或烧录）
subgen.bat 视频.mp4 -t en --bilingual
#   → 视频.zh.srt   视频.en.srt   视频.zh-en.bilingual.srt

# 多轨 MKV：一个文件，播放器里切中/英
subgen.bat 视频.mp4 -t en --mux
#   → 视频.softsub.mkv   （含 中文 / English 两条字幕轨）

# 只要译文，不要中文（省得文件多）
subgen.bat 视频.mp4 -t en --only-translated
#   → 视频.en.srt
```

**为什么默认出两份而不是只出译文**：只出译文的话原文就没了，
  
之后想对照、想改译、想重新烧录双语都做不到——重跑一遍又是一次 ASR 开销。
  
多留一份文件几乎零成本（几十 KB），但省掉很多返工。

**多轨和双语的关系**：`--mux` 时不额外封装双语轨，因为播放器里
  
同时打开中文轨和英文轨就能看到双语效果，再塞一条双语轨是冗余的。

### 3.1 先看怎么用

```bash
# 中 → 英，只出英文字幕
subgen.bat 视频.mp4 -t en

# 中英双语同屏（原文在上、译文在下）
subgen.bat 视频.mp4 -t en --bilingual

# 翻成日文，用大模型（质量更好）
subgen.bat 视频.mp4 -t ja --mt-backend llm

# 配术语表，专有名词不会被乱翻
subgen.bat 视频.mp4 -t en --mt-glossary 术语表.txt

# 批量翻译整个目录
subgen.bat "素材/*.mp4" -t en --bilingual -o "双语字幕/"
```

产出文件名会自动带语言标记：`视频.zh.srt`、`视频.en.srt`、`视频.zh-en.bilingual.srt`。

### 3.2 两个后端，怎么选

|            | 离线后端（默认）         | LLM 后端        |
| ---------- | ---------------- | ------------- |
| 需要联网       | 仅首次下载模型          | 每次都要          |
| 需要 API Key | 不需要              | 需要            |
| 费用         | 免费               | 按量计费          |
| 速度         | **极快**（实测 4ms/条） | 取决于接口，通常几秒/批  |
| 质量         | 中等，直译为主          | **优秀**，懂语境和口语 |
| 语言对数       | 100 个方向          | 模型支持多少就有多少    |

`--mt-backend auto`（默认）会**自动判断**：检测到 API Key 就用 LLM，否则走离线。

**实测结论：离线后端适合「能看懂就行」的场景，LLM 适合对外发布。**

同一句 `我叫你帮男主是帮男主救女主`：

```
离线    → I told you to help the master.
LLM     → I told you to help the male lead save the female lead.
```

口语和网络用语差距更明显：

```
卧槽,角色不是定好了吗,女友是人啊
离线    → Shit, I thought the part was set. The girl's a man.    ← 「女友是人」翻反了
记得点赞投币收藏,我们下期再见
离线    → Remember to have a nice collection.                    ← 网络用语直译
```

### 3.3 术语表：最实用的质量杠杆

离线模型对专有名词会强行「意译」，这是它最大的短板。术语表能直接解决：

```
# 术语表.txt  —— 每行一条，支持 = / => / ：
男主=the male lead
女主=the female lead
妙脆角猫=Cream Cat
双马尾=twin tails
```

实测效果：

| 原文   | 不带术语表             | 带术语表                  |
| ---- | ----------------- | --------------------- |
| 男主   | the master ❌      | **the male lead** ✅   |
| 女主   | the princess ❌    | **the female lead** ✅ |
| 妙脆角猫 | Cream Cape Cats ❌ | **Cream Cat** ✅       |
| 双马尾  | ponytail ⚠️       | **twin tails** ✅      |

**原理**：不是译后替换（那样语序会乱），而是译前把术语换成 `XTERM0X` 这类占位符。
  
模型不认识这种 token，只能原样保留且位置正确，译完再还原。
  
这是实测验证过的方案——试过 `[T0]` 这类格式会被模型改写，`XTERM0X` 最稳。

批量处理同一账号的视频时，术语表建一次就能长期复用。

### 3.4 大模型后端配置

支持任意 **OpenAI 兼容接口**（国内主流服务商基本都是）。

#### 界面上怎么配

「翻译 → 翻译引擎」选 **大模型**，下面会展开完整配置：

| 项 | 说明 |
|---|---|
| **服务商** | 下拉选一个，**端点和推荐模型会自动填好**，不用去翻文档 |
| **API Key** | 点👁可显示明文；点「去申请」直接跳转对应控制台 |
| **模型** | 已按服务商预填，可改成任意模型名 |
| **接口地址** | 已预填，用中转/自建时改成自己的 |
| **测试连接** | **强烈建议点一下** —— 几秒就能确认配置能不能用 |

内置 9 家预设：

| 服务商 | 端点 | 默认模型 | 说明 |
|---|---|---|---|
| **DeepSeek** ⭐ | `api.deepseek.com/v1` | `deepseek-chat` | 便宜、中文好，**翻译首选** |
| 阿里云百炼 | `dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-plus` | 国内直连，有免费额度 |
| 月之暗面 Kimi | `api.moonshot.cn/v1` | `moonshot-v1-8k` | 长文本友好 |
| 智谱 GLM | `open.bigmodel.cn/api/paas/v4` | `glm-4-flash` | 有免费模型 |
| 硅基流动 | `api.siliconflow.cn/v1` | `Qwen/Qwen2.5-7B-Instruct` | 聚合多家开源模型 |
| 火山方舟（豆包） | `ark.cn-beijing.volces.com/api/v3` | `doubao-pro-32k` | 需先在控制台建接入点 |
| OpenAI | `api.openai.com/v1` | `gpt-4o-mini` | 需要能访问外网 |
| **本地 Ollama** | `127.0.0.1:11434/v1` | `qwen2.5:7b` | **完全本地，不需要 Key** |
| 自定义 / 中转 | 自填 | 自填 | 任何兼容接口 |

#### 命令行怎么配

```bash
subgen.bat 视频.mp4 -t en --api-key sk-xxx \
  --api-base https://api.deepseek.com/v1 --llm-model deepseek-chat
```

#### 环境变量（配一次长期用）

```bash
set SUBGEN_API_KEY=sk-xxx
set SUBGEN_API_BASE=https://api.deepseek.com/v1
set SUBGEN_LLM_MODEL=deepseek-chat
```

也可以只设常见变量，程序会自动识别并匹配端点：
`DEEPSEEK_API_KEY` / `OPENAI_API_KEY` / `DASHSCOPE_API_KEY` /
`MOONSHOT_API_KEY` / `ARK_API_KEY` / `SILICONFLOW_API_KEY` / `ZHIPU_API_KEY`

> 已经用环境变量配好的情况下，界面会提示"检测到 XX 已配置 Key，可直接用"，
> 不用重复填。

#### 配不上时先看这里

LLM 配置**最容易错的不是 Key，而是端点**。点「测试连接」会给出具体原因：

| 报错 | 原因 | 怎么办 |
|---|---|---|
| `HTTP 401` | Key 无效或过期 | 去控制台重新生成 |
| `HTTP 404` | **端点路径不对** | 多半是漏了 `/v1`，对照上表检查 |
| `HTTP 402` | 余额不足 | 充值 |
| `HTTP 429` | 触发限流 | 稍后再试或换模型 |
| `连不上：…` | 网络/代理问题 | 检查网络；OpenAI 需能访问外网 |
| `没有填 API Key` | Key 为空 | 只有本地服务（Ollama）可以留空 |

**关于中转服务**：用第三方中转时端点填服务商给的地址（通常以 `/v1` 结尾），
服务商选「自定义 / 中转」。测试通过后，界面显示的模型名以服务商回显的为准。

#### 让译文更贴语境

用 `--mt-context` 告诉模型内容风格，提升明显：

```bash
subgen.bat 视频.mp4 -t en --mt-backend llm \
  --mt-context "游戏解说视频，口语化，可保留网络用语，不要过度正式"
```

### 3.5 翻译相关的全部参数

| 参数                         | 说明                                   | 默认              |
| -------------------------- | ------------------------------------ | --------------- |

| `--mt-glossary FILE`       | 术语表文件路径（也可直接传字符串）                    | —               |

### 3.6 语言支持范围

离线后端有 **100 个直连方向**（`--list-langs` 可查全部）：

- 中英互译、日英、韩英、法英、德英、西英、俄英、葡英、意英、阿英、
    
  泰英、越英、印尼英、印地英 ……
- **其他语言对自动经英文中转**（如 日→中 走 日→en→zh），质量会略降

要用任意语言对，直接用 LLM 后端——不受这个限制。

## 四、常用命令

```bash
# 一次导出多种格式
subgen.bat 视频.mp4 -f srt vtt ass

# 中文视频显式指定语言（比自动检测更稳、更快）
subgen.bat 视频.mp4 -l zh

# 追求最高精度
subgen.bat 视频.mp4 -m large -l zh

# 术语/人名识别不准时，塞提示词
subgen.bat 视频.mp4 -l zh --prompt "参会人：汪兴祥、张伟。产品名：WorkBuddy、OceanBase"

# 只处理 1:30 到 3:00 这一段
subgen.bat 视频.mp4 --start 90 --end 180

# 直接烧成硬字幕视频（适合发抖音/视频号）
subgen.bat 视频.mp4 --burn

# 无损封装成 MKV 软字幕（画质不变，播放器可开关）
subgen.bat 视频.mp4 --mux

# 批量处理整个目录
subgen.bat "素材/*.mp4" -o "字幕/"

# 只要纯文本稿（不要时间轴）
subgen.bat 音频.mp3 -f txt
```

## 六、模型怎么选

| 模型       | 体积     | 显存     | 适合                 |
| -------- | ------ | ------ | ------------------ |
| `small`  | 480 MB | 1.2 GB | 先试水、纯 CPU          |
| `medium` | 1.5 GB | 2.5 GB | 老显卡、均衡             |
| `turbo`  | 1.6 GB | 2.5 GB | **默认推荐**，速度与精度最佳平衡 |
| `large`  | 3.1 GB | 4.7 GB | 难缠音频、要求最高精度        |

模型首次运行自动下载到 `models/`，之后离线可用。默认走 hf-mirror 国内镜像，
  
加 `--no-mirror` 可切回官方源。

翻译模型（离线后端）单独放在 `models/mt/`，每个语言方向约 75 MB，同样首次自动下载。

| **设置**   | 识别（模型/语言/降噪）、翻译（目标语言/双语/引擎）、输出（格式/目录）、成片（烧录/多轨）、排版、高级 |

### 怎么判断程序还在处理，还是卡死了

大模型 + 长视频时，某个步骤可能要跑几十秒到几分钟。界面现在会**明确告诉你还在干活**：

| 界面表现                        | 含义                       |
| --------------------------- | ------------------------ |
| 状态栏显示 `（仍在处理，本阶段已用 1:23）`   | 该阶段耗时长，但**正在跑**，计时器在走    |
| 状态栏显示 `已用 0:45 · 预计剩余 0:38` | 有速度数据，给出了剩余时间预估          |
| 进度条变成**流动的斜纹**              | 当前步骤没有细粒度进度（如加载模型），但程序在跑 |
| 日志里出现新的时间戳                  | 有新的步骤完成                  |
| 日志 25 秒没有任何新增               | 可能真卡了，看下方排查              |

**判断是否真卡死的三个方法**：

```bash
# 1. 看 GPU 有没有在算（utilization 是否 > 0）
nvidia-smi --query-gpu=utilization.gpu,memory.used --format=csv

# 2. 看进程 CPU 时间是否在增长（隔几秒看两次，涨了就是在干活）
#    Windows 任务管理器 -> 详细信息 -> 找 python.exe 看"CPU 时间"

# 3. 点「停止」能否立即响应（能响应说明主线程是活的）
```

**常见的"看起来卡住"其实正常**：

| 现象              | 真实原因                      | 大概要等多久  |
| --------------- | ------------------------- | ------- |
| 首次运行卡在"下载模型"    | 正在下载模型，**界面有真实百分比和 MB 数** | 见下表     |
| 卡在"加载识别模型"      | large 模型读进显存，机械盘更慢        | 10~60 秒 |
| 卡在"语音识别中"       | ASR 推理中，进度条在走就没事          | 见下表     |
| 卡在"翻译中"（LLM 后端） | 在等大模型接口返回                 | 几秒~几十秒  |

**模型下载耗时参考**（走 hf-mirror 国内镜像，实测约 3~5 MB/s）：

| 模型      | 体积         | 下载约需     |
| ------- | ---------- | -------- |
| `base`  | 145 MB     | 30 秒     |
| `small` | 480 MB     | 2 分钟     |
| `turbo` | 1.5 GB     | 5 分钟     |
| `large` | **2.9 GB** | 10~15 分钟 |

下载**支持断点续传**：中途取消或断网后重来，会从已下载的位置继续，
  
不会从头开始。所以放心，2.9 GB 不会白下。

**参考速度**（本机 GTX 1080 Ti + int8）：

| 模型      | 速度   | 1 分钟视频约需 | 10 分钟视频约需 |
| ------- | ---- | -------- | --------- |
| `small` | ~25x | 3 秒      | 25 秒      |
| `turbo` | ~12x | 5 秒      | 50 秒      |
| `large` | ~5x  | 12 秒     | 2 分钟      |

如果实际耗时远超上表，多半是**有其他程序在抢 GPU**（浏览器、视频播放器、
  
游戏甚至某些聊天软件都会占显存）。可以先关掉它们再试。

### 便捷操作一览

- **拖拽排序** —— 处理顺序由你定，拖一下就行
- **内嵌字幕预览** —— 生成后直接在界面里看中英对照，不用开播放器
- **打开输出目录** —— 一键在资源管理器里定位文件
- **记住上次设置** —— 模型、语言、术语表、输出目录全都自动恢复
- **随时停止** —— 批量跑到一半发现设置错了，点「停止」即刻中止


### 为什么用 pywebview 而不是 Qt / tkinter

| 方案 | 额外体积 | 说明 |
|---|---|---|
| **pywebview + HTML/CSS** ✅ | **≈1 MB** | 用系统自带的 WebView2 渲染，界面用 Web 技术写，可做复杂交互 |
| PySide6 / PyQt6 | +80 MB | 观感专业，但要额外背 80 MB 运行时 |
| tkinter | 0 MB | 标准库，但复杂布局和现代观感很难做 |
| Gradio | +30 MB | 开发最快，但每次要开浏览器 + 控制台窗口，不符合「双击就用」 |

选它的理由：**体积几乎不增**（项目 venv 里 2.3 GB 全是 CUDA 库，GUI 这层没必要再叠 80 MB）、
**界面表现力足够**（折叠面板、进度条、拖拽都是 Web 强项）、**核心逻辑零改动**（复用同一套 `run_one()`）。

### 拖放是怎么实现的

pywebview 6.x **没有暴露拖放接口**，而浏览器沙箱出于安全限制，HTML5 拖放只能拿到
文件名、拿不到真实路径。所以纯前端方案做不到。

本工具走的是 WinForms 事件通道：pywebview 的 Windows 后端本身就是 pythonnet 驱动的
WinForms，于是直接给主窗体挂 `DragDrop` 事件（`subgen/dropbridge.py`），拿到真实路径后
推给前端。这是唯一可靠的方案。

> 若这条路在某些环境下失效，界面会自动回退到「按文件名在桌面/下载等常见目录里查找」，
> 再不行就提示你用「添加文件」按钮——不会静默失败。


### 进度是怎么推给界面的（一个踩过的坑）

这里有个不显眼但很致命的问题：**后台处理线程不能直接操作界面**。

pywebview 的 `evaluate_js()` 看着能用，实际内部是
`Invoke(...)` 投递到 UI 线程 + `semaphore.acquire()` **同步等结果**。
从后台处理线程调用时，UI 线程正忙于自己的消息循环，信号量久久等不到，
处理线程就被活活卡死。表现就是：**点开始后界面一直显示「待处理」，
进度完全不动，而且不报任何错。**

绕过它的两条路也都不行：
- 带 callback 调 `evaluate_js` —— 内部仍然 `semaphore.acquire()`，照样阻塞
- 直接调 WebView2 的 `ExecuteScriptAsync` —— COM 组件要求 UI 线程，
  从后台线程调会**静默失败**（不抛异常，但脚本没执行）

**最终方案：队列 + 轮询。**

```
后台线程 --(_emit 入队，只碰 deque)--> 事件队列
                                        ↑
前端每 150ms --(poll_events 取走)-------┘  ← 这一步天然在 UI 线程上
```

后台线程完全不碰 UI，前端主动来取，跨线程问题从根上消失。
顺带还解决了「任务启动太快、前端还没准备好就收到事件」的丢失问题——
事件会先缓存在队列里，等前端来取。

实现见 `subgen/gui.py` 的 `_emit()` / `poll_events()` 与界面里的 `startPolling()`。

### 底部时间轴（波形 + 字幕条）

![时间轴](out/界面校对工作台.png)

时间轴分三层，一眼看清"什么时候有人说话、字幕盖在哪一段"：

| 层 | 内容 |
|---|---|
| 刻度 | 时间标尺，缩放时自动调整间隔 |
| 字幕条 | 每句一个方块，**可拖动改时间、拖左右边缘改起止** |
| 波形 | 音频振幅，**说话间隙会自动淡黄标出**（对着静音区调边界特别准） |

**能做什么**：

- **拖字幕条** —— 整段提前/延后，拖完自动跳到该句起点试听
- **拖左右边缘** —— 精确调整起止时间（间距小于 0.25 秒会自动拦住）
- **点刻度区** —— 播放头跳过去
- **缩放滑块** —— 从看全片到看清单字，范围 8~600 px/秒
- **播放头自动跟随** —— 播放时时间轴自动滚动，不用手动找
- **拆分 / 合并** —— 长句在播放头处切开；过短的两句合并
- **撤销 / 重做** —— `Ctrl+Z` / `Ctrl+Y`，最多 80 步

### 快捷键

| 键 | 作用 |
|---|---|
| `空格` | 播放 / 暂停 |
| `R` | 重播当前句 |
| `↑` `↓` | 上一句 / 下一句 |
| `回车` | 跳到下一句并聚焦（在编辑框里时） |
| `Ctrl+S` | 保存 |
| `Ctrl+Z` / `Ctrl+Y` | 撤销 / 重做 |
| `Esc` | 退出编辑 |

播放速度可循环切换（**1.0× → 1.25× → 1.5× → 2.0× → 0.75× → 0.5×**），
方言听不清时用 0.75× 慢放非常有用。

### 改动可视化

- **黄色高亮** = 这句改过（右上角有「已改」标记）
- 顶部实时显示 `共 11 句 · 2 处已改 · 未保存`
- 可以点「已改」筛选，**只看改动过的句子**做二次检查
- 保存时**自动生成 `.bak` 备份**，改错了能找回来

### 保存时的自动保护

保存前会做两件事，避免产出坏字幕：

1. **按时间排序** —— 顺序乱了自动理顺
2. **修掉时间交叉** —— 上一句的结束时间压到下一句开始之后时，自动拉开

所以你手滑把时间轴改乱了，保存出来的仍是合法字幕。

### 技术说明：为什么能实现

- **播放不用转码**：素材通常是 H.264 + AAC，WebView2 原生支持，直接播
- **能任意跳转**：为此专门实现了支持 HTTP Range 的本地媒体服务
  （Python 内置的 `SimpleHTTPRequestHandler` **不支持 Range**，
  实测拖动进度条会退化成全量下载，对"反复听某句"完全不可用）
- **波形怎么来的**：不用 Web Audio 解码整个文件（长音频要几十秒且吃内存），
  而是让 ffmpeg 降采样成低采样率单声道 PCM、再算每点峰值 ——
  34 秒视频只要 **0.4 秒**，数据量 6.8 KB。结果**按区间缓存**，
  拖动缩放时不会重复提取
- **跨源问题**：界面由 pywebview 的 http_server 提供（端口 A），
  媒体由媒体服务提供（端口 B），两者不同源。所以媒体服务必须发
  `Access-Control-Allow-Origin`，否则 Web Audio 会**静默产出静音**（不报错，极难查）
- **全程本地**：媒体服务只绑 `127.0.0.1`，且只服务**注册过**的文件，
  不会把磁盘暴露出去
- **独立窗口**：校对需要大播放区 + 长列表 + 时间轴，用满屏幕更舒服

## 九、针对本机的特别说明（GTX 1080 Ti）

1080 Ti 是 Pascal 架构（CC 6.1），**没有 Tensor Core**。这带来两个反直觉的坑：

**坑一：`float16` 不能用。**
NVIDIA 在 Pascal 消费级卡上把 FP16 吞吐人为限制到 FP32 的 1/64，
指定 `float16` 不但慢，还会直接报错。

**坑二：`float32` 也别用，`int8` 才是最优解。**

这点很容易想错——既然 FP16 不行，那"稳妥"的 `float32` 总没错吧？
实测数据（34 秒中文音频，本机）：

| 模型 | 精度 | 识别耗时 | 速度 |
|---|---|---|---|
| turbo | float32 | 32.4s | 1.0x |
| turbo | **int8** | **2.9s** | **11.7x** |
| large | float32 | 125.4s | 0.3x |
| large | **int8** | **6.3s** | **5.4x** |

**`int8` 比 `float32` 快 11~20 倍**，而识别结果几乎完全一致
（tokens 数完全相同：112 vs 112、111 vs 111）。

> 这条是踩过坑才知道的：早期版本在 Pascal 卡上选 `float32`，
> 结果 large 模型跑 34 秒音频要 **125 秒**（0.3x 实时），
> 用户以为程序卡死了。换成 `int8` 后同样的活只需 6.3 秒。

本工具现在**在所有显卡上都默认 `int8`**（不限 Pascal），无需手动干预。
想自己对比时，用 `--compute-type float32` 跑一次就能看出差距。

另外一个要点：**不要把 `--jobs` 调大跑并行**。单个 large 模型已经吃满 GPU，
并行只会争抢显存导致整体变慢。批量处理时本工具默认串行复用同一个模型实例，
省掉重复加载开销，这才是正确的批量姿势。

## 十、识别有错误怎么调

字幕识别出错很常见，但**不同类型的错误要用不同手段**。先对症再下药，比盲目换模型有效得多。

### 9.1 先判断错误类型

| 现象 | 例子 | 原因 | 用什么治 |
|---|---|---|---|
| **同音/近音字** | 妙翠脚 → 妙脆角 | 模型听音猜字 | 提示词 / 纠错表 |
| **专有名词** | 阿珍 → 阿真 | 模型不认识这名字 | 提示词 / 术语表 |
| **繁体输出** | 還沒有發育 | 训练数据繁体占比高 | 自动转简体（默认开） |
| **成语被拆碎** | 笑掉大牙 → 小调大雅打 | 方言+语速快 | 换 large 模型 / 纠错表 |
| **方言用词** | 四川话"啥子"识别成"啥" | 模型按普通话训练 | 提示词 / 纠错表 |
| **漏字** | 我一讲情错 → 我一讲错 | VAD 切掉了音 | 调 `--no-vad` 试试 |
| **整段重复** | 同一句出现两次 | 模型幻觉 | 已内置去重；仍出现则提高 `--beam-size` |

### 9.2 三招，按性价比排序

**第一招：填提示词（最省事，效果最明显）**

```bash
subgen.bat 视频.mp4 -l zh --prompt "妙脆角猫、雪域高原、繁殖季"
```

界面上对应「识别纠错 → 提示词」。

> **实测数据**（方言短剧，同一段音频）：
>
> | 配置 | 术语错误 |
> |---|---|
> | large 无提示词 | **6 处**（妙翠角） |
> | large + 提示词 | **0 处** ✅ |
>
> 有意思的是：**large 不加提示词反而比 turbo 更差** ——
> 大模型更"自信"，会把没见过的词替换成它认为更常见的说法。
> 所以用大模型时，提示词更必要。

**第二招：纠错表（对已生成的字幕也能补救）**

知道错在哪就直接替换，不用重新跑 ASR：

```bash
# 方式一：内联
subgen.bat 视频.mp4 --fixups "妙翠脚=妙脆角、血域=雪域"

# 方式二：文件（推荐，可复用）
subgen.bat 视频.mp4 --fixups 纠错表.txt
```

`纠错表.txt` 格式（每行一条，`=`、`=>`、`：` 都行）：

```
# 井号开头是注释
妙翠脚=妙脆角
血域=雪域
小调大雅打=笑掉大牙
```

界面上对应「识别纠错 → 纠错表」，直接填多行文本。

**第三招：换模型 / 调参数**

```bash
# 换更大的模型（更准但更慢）
subgen.bat 视频.mp4 -m large -l zh

# 提高束搜索宽度（默认 5，提到 8~10 更稳）
subgen.bat 视频.mp4 -l zh --beam-size 10

# 疑似被 VAD 误切导致漏字时
subgen.bat 视频.mp4 -l zh --no-vad
```

### 9.3 三个开关的关系（别搞混）

| 设置 | 作用于 | 什么时候用 |
|---|---|---|
| **提示词** | 识别阶段（影响听音） | 有专有名词、需要引导风格 |
| **术语表** | **识别 + 翻译**（两处都用） | 术语既要识别对、又要翻译对 |
| **纠错表** | 识别**之后**（后处理替换） | 已知具体错词，直接改掉 |

> **术语表在识别阶段也会生效** —— 表里的原词会自动作为提示词喂给模型，
> 从源头减少同音字错误；译词则用于后续翻译。一份表管两头。

### 9.4 繁体自动转简体

中文识别结果默认自动转简体（Whisper 常输出繁体）。要保留原文繁体时：

```bash
subgen.bat 视频.mp4 -l zh --no-simplify
```

界面上关掉「识别纠错 → 转简体」即可。

### 9.5 方言内容怎么办

方言是识别准确率的最大杀手。实测（四川方言短剧）即便用 large 模型，
仍会有「啥子→啥」「巴适」这类词识别不准，因为 **Whisper 主要按普通话训练**。

实用做法是**组合拳**：

```bash
subgen.bat 剧集.mp4 -l zh -m large \
  --prompt "四川方言短剧。妈、娃儿、啥子、巴适、老汉儿" \
  --fixups "纠错表.txt"
```

- 提示词里写上方言常用词，模型更容易"听对"
- 纠错表积累这个剧的高频错词，**下一集直接复用**
- 同一部剧的术语和错词模式高度相似，表建一次能一直用

> 如果方言是长期刚需，可以考虑接 FunASR 的 SenseVoice（中文 CER 约为
> Whisper 的 1/2.7，且原生支持粤语）。本工具的 ASR 引擎是独立模块，
> 加一个后端即可，其余管线（抽音轨、断句、翻译、多格式输出）完全复用。

## 十一、去除视频自带的字幕

有些视频本身带了字幕（尤其下载来的素材），直接生成新字幕会**新老重叠**。
这个功能用来把原字幕遮盖掉。

### 11.1 先分清两种情况

| 类型 | 能否"删除" | 怎么做 |
|---|---|---|
| **软字幕**（独立字幕流） | ✅ 可以真正删掉 | 用 `ffmpeg -sn` 直接剥离，画质无损 |
| **硬字幕**（烧进画面像素） | ❌ 只能**遮盖** | 把字幕区糊掉，这是本功能处理的 |

判断方法：`--desub-preview` 会顺带告诉你。如果 `ffprobe` 显示有 subtitle 流就是软字幕。

> **硬字幕的固有限制**：像素里已经不存在"这是字幕"的信息了，
> 所以只能糊掉。**字幕压在纯色/虚化背景上几乎完美；压在人脸、细密纹理上会留下痕迹。**

### 11.2 怎么用

```bash
# 先检测字幕位置（不改动文件）
subgen.bat 视频.mp4 --desub-preview

# 自动检测 + 遮盖，然后正常生成字幕（一步到位）
subgen.bat 视频.mp4 --desub auto -l zh -t en

# 只输出干净视频，不生成字幕（配合 srt 软字幕用，画质无损）
subgen.bat 视频.mp4 --desub auto --desub-only

# 手动指定区域（检测不准时）
subgen.bat 视频.mp4 --desub "14,874,691,68"

# 顺带遮盖顶部标题（默认只处理底部字幕）
subgen.bat 视频.mp4 --desub auto --desub-top
```

界面上对应的位置是「**原字幕处理**」区，勾选后可选**自动检测 / 底部预设 / 手动指定**，
点「检测」按钮会把识别出的区域自动填进输入框。

### 11.3 两种输出模式

| 模式 | 命令 | 用途 |
|---|---|---|
| **只出干净视频** | `--desub-only` | 视频不带字幕，字幕单独给 `.srt`。<br>播放器/B站/YouTube 都能挂软字幕，**画质无损、字幕随时能改** |
| **一步到位出成片** | `--desub auto --burn` | 遮盖旧字幕 + 烧录新字幕，直接产出可发布的成品 |

> 推荐前者：不用二次编码，字幕改起来方便。
> 后者适合"必须交付单个文件、平台只认硬字幕"的场景。

### 11.4 遮盖方式怎么选

| 方式 | 效果 | 说明 |
|---|---|---|
| **`blur` 模糊** ⭐ | 字迹完全糊掉，保留背景明暗 | **默认**，观感最自然 |
| `pixelate` 马赛克 | 最彻底，绝对看不出原文 | 风格明显，适合不介意马赛克的场合 |
| `delogo` 边缘插值 | ⚠️ **宽字幕带会出竖条纹** | 仅在窄条遮挡（如台标）时好用 |
| `box` 半透明黑条 | ❌ 对浅色背景的字无效 | 基本不推荐 |

**实测数据**（720×1280 竖屏，字幕带 691×68）：

| 方式 | 结果 |
|---|---|
| blur（降采样 1/40） | 6 个采样点的高亮像素**全部为 0**，最大亮度从 255 降到 218 以下 ✅ |
| delogo | 出现规则竖向条纹，比原字幕更显眼 ❌ |

**为什么 blur 用"降采样"而不是 `boxblur`**：`boxblur` 的色度半径上限只有 **13**，
对这种粗体大白字根本糊不透（实测字迹依然清晰可读）。
改成先把区域缩到 1/40 再放大回来，等效模糊半径远超这个限制。

### 11.5 关于自动检测

原理：抽样多帧，找"高亮像素密集的横向条带"（硬字幕通常是白字+描边）。

**检测会给出置信度，请留意**：

```
检测区域: x=14 y=874 w=691 h=68
相对位置: y 68.3% ~ 73.6%
置信度  : 0.72  （条带位于画面下方）
```

- **置信度 > 0.6 且位置在画面下半部** → 可信
- **置信度偏低或位置偏上** → 多半是画面里的高光区被误判了（白猫、浅色衣服都会骗过算法）

**检测不准时怎么办**：
1. 用 `--desub-preview` 看它给的建议区域
2. 手动量一下真实位置，用 `--desub "x,y,w,h"` 指定
3. 或者直接用 `--desub bottom` 按预设遮盖底部

> 字幕位置在**同一部剧里通常固定**，所以量一次就能一直用。

### 11.6 相关参数

| 参数 | 说明 |
|---|---|
| `--desub [区域]` / `--remove-subs` | 去字幕。区域可为 `auto`、`bottom`/`bottom2`/`top` 预设、或 `x,y,w,h`（多个用 `;` 隔开） |
| `--desub-top` | 同时遮盖顶部标题区 |
| `--desub-only` | 只输出干净视频，不生成字幕 |
| `--desub-preview` | 只检测位置并报告，不处理文件 |

## 十二、常见问题

**Q：我改了界面/代码，重启后看到的还是旧界面？需要编译吗？**

**不需要编译**。`启动界面.bat` 是直接跑源码的（`pythonw -m subgen.gui_main`），
Python 和 HTML 都改完即生效。

如果重启后仍是旧界面，那是 **WebView2 的缓存**在作怪 —— 它会强缓存本地页面的旧版本，
而且不理会标准的 `no-cache` 头，清浏览器缓存也不一定管用。

**已经在代码里根治了**：页面 URL 会带一个基于文件修改时间的版本号
（`index.html?v=1792724461`），文件一改 URL 就变，缓存自动失效。
启动时也关掉了 WebView2 的持久化存储做双保险。

> 万一还遇到，说明这个机制被改坏了 —— 检查 `subgen/gui_main.py` 里
> 是否还在用 `versioned_url()` 加载页面。
> `tests/verify_gui_fresh.py` 会专门守这个，可以跑一下确认。

**Q：任务明明跑完了，状态栏还一直显示"处理中"？**

已在 v1.1 修复。根因是进度心跳线程没被停止 ——
`CallbackReporter` 的心跳靠 `file_done()` / `finish()` 结束，
而早期代码从头到尾没调用过这两个方法，于是任务结束后
心跳仍在每秒推送进度，把状态栏刚写上的"全部完成"覆盖掉，
同时让日志被同一句话刷屏（实测刷到 732 条）。

现在三层防护：任务循环里正确调用 `file_done()`、
收尾用 `finally` 兜底调 `finish()`、心跳自身在阶段结束时也会退出。
`tests/verify_progress_lifecycle.py` 专门守这个。

**Q：日志里全是"导出字幕文件…"这类重复内容？**

已在 v1.1 优化。日志**不再复读状态栏**（阶段进展由状态栏和进度条呈现），
只记**结果与异常**；每行压成一条短摘要（短文件名 + 条数 + 耗时 + 倍率 + 输出位置），
完整路径鼠标悬停可见。

**Q：字幕断句很奇怪，一句话被切碎了？**
调大 `--max-chars`（比如 25）让每行装更多字；或调大 `--max-duration`。

**Q：出现了原文里没有的内容（幻听）？**
常见于纯音乐段落或强背景噪声。确认没加 `--no-vad`；再不行把 `--beam-size` 提到 8，
或换 `large` 模型。

**Q：专业名词识别错？**
转录阶段用 `--prompt "正确词1、正确词2"`（影响识别）；
翻译阶段用 `--mt-glossary`（影响译文）。

**Q：翻译出来不通顺、口语梗翻错了？**
换 LLM 后端（`--mt-backend llm`），并用 `--mt-context` 描述内容风格。
离线模型是逐句直译，不懂笑点，这是架构决定的，不是 bug。

**Q：能识别/翻译粤语吗？**
识别可以，但 Whisper 常把粤语当普通话转成书面语，翻译也会失真。
要求高的话建议改用 FunASR 的 SenseVoice 模型（中文 CER 约为 Whisper 的 1/2.7）。

**Q：CPU 能跑吗？**
能。`small` 模型约 2~3 倍实时，`medium` 约 1 倍实时，`large` 会比播放还慢。
有 N 卡务必用 GPU。

**Q：字幕编码会不会乱码？**
SRT 输出带 UTF-8 BOM（兼容老旧播放器如 MPC-HC），VTT/ASS 输出纯 UTF-8。
现代播放器（PotPlayer、VLC、IINA）全部正常。

```
subtitle-gen/
├── 启动界面.bat          ★ 图形界面入口（双击即用）
├── install.bat          一键安装
├── subgen.bat           命令行入口
├── requirements.txt     依赖清单（pywebview 为可选项）
│
├── webui/
│   ├── index.html       主界面（HTML/CSS/JS 单文件，无构建步骤）
│   └── review.html      字幕校对工作台界面
│
├── subgen/
│   ├── cli.py           命令行入口、参数解析
│   ├── tasks.py         任务编排（CLI 与 GUI 共用，核心逻辑在这）
│   ├── reporter.py      进度上报接口（终端/界面两种实现）
│   ├── gui.py           界面桥接（JS 调用 → 核心逻辑）
│   ├── gui_main.py      界面进程入口
│   ├── review.py        校对工作台桥接
│   ├── mediaserve.py    本地媒体服务（支持 HTTP Range，供播放器任意跳转）
│   ├── subio.py         字幕文件读写（容错解析 + 回写）
│   ├── waveform.py      波形峰值提取（供时间轴绘制）
│   ├── desub.py         硬字幕遮盖（去除原视频字幕）
│   ├── dropbridge.py    拖放路径桥接（WinForms 事件）
│   ├── models.py        模型预设、显卡探测、镜像下载
│   ├── audio.py         ffmpeg 封装（抽音轨/烧录/多轨封装）
│   ├── engine.py        faster-whisper 推理封装
│   ├── segmenter.py     智能断句 + 折行（核心算法）
│   ├── translator.py    翻译引擎（离线 + LLM 双后端）
│   └── formats.py       SRT/VTT/ASS/LRC/TXT 输出
│
├── tests/
│   ├── test_smoke.py           93 项单元测试（断句/格式/翻译/纠错/多轨）
│   ├── verify_log.py           界面日志功能验证（Edge 无头 + mock）
│   ├── verify_e2e_gui.py       界面端到端验证（真实窗口 + 真实视频）
│   ├── verify_review.py        校对工作台端到端验证
│   ├── verify_timeline.py      时间轴结构与交互验证
│   ├── verify_llm_config.py    大模型配置界面验证
│   ├── verify_gui_fresh.py     GUI 是否加载最新界面（防缓存回归）
│   ├── verify_progress_lifecycle.py  进度心跳生命周期（防状态栏卡死）
│   ├── preview_review.py       生成工作台界面预览图
│   └── probe_webaudio.py       Web Audio 可行性探测
└── models/              模型缓存（首次运行自动创建）
    ├── <ASR 模型>
    └── mt/              翻译模型
```

**架构要点**：处理的真正逻辑在 `tasks.py`，命令行和图形界面都调它，
所以两者行为**永远一致**，不存在「界面能跑命令行报错」这种双份维护的问题。
`reporter.py` 把进度输出抽象成接口——终端实现打进度条，界面实现推 JS 回调，
核心代码不需要知道自己在被谁调用。

不需要也不依赖 PyTorch —— 整条链路只有 ffmpeg + CTranslate2，
装包体积小、启动快。翻译只依赖 sentencepiece（约 1 MB），
连 HTTP 请求都用标准库发的，没引入 requests。
