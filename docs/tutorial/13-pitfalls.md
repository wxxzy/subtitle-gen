# A 组 · 性能异常

## 坑 1：int8 不是降级，float32 才是灾难

### 现象

large 模型跑 34 秒音频，用了 **125 秒**（0.3x 实时）。
40 分钟的视频要跑 2 小时以上。用户以为程序挂了。

### 当时的误判

> "float16 报错 → 那退回 float32 最稳妥"

这个思路本身没错（float32 确实最安全），但它**牺牲了 20 倍速度**换来的安全感是虚的。

### 真相

```
GTX 1080 Ti（Pascal CC 6.1）实测，34 秒音频：

模型      float32           int8
turbo     32.4s (1.0x)      2.9s (11.7x)
large    125.4s (0.3x)      6.3s (5.4x)
```

**关键不只是快，还有：识别结果的 tokens 数完全一致。**

### 思维盲区

我只在「float16 和 float32」之间选，**完全没想到 int8 这条路**。

**墨菲定律的变体**：当你把选项限定在两个里，就会忘记第三个可能更好。

### 修复

```python
# 一律优先 int8，与显卡新旧无关
out["recommended_compute_type"] = "int8"
```

### 迁移价值

> **遇到"两个选项都不好"时，先问：是不是选项本身就没列全？**

## 坑 2：pywebview 的 evaluate_js 会卡死线程

### 现象

点"开始生成"后，界面**完全不动**，进度一直 0。
**没有任何报错**，看起来像死机。

### 误判

一开始以为是 ASR 太慢、模型加载卡住、显卡驱动问题……
查了两小时才发现**根本没走到识别那一步**。

### 真相

```python
# 后台线程里调用
self._window.evaluate_js(js)
```

pywebview 内部是**同步阻塞**：

```
后台线程：semaphore.acquire() 等待
UI 线程：忙于消息循环，不知道有人在等
→ 死锁
```

而且**异常被吞掉了**。

### 修复

后台线程只往队列塞事件，由前端轮询取（详见 11 篇）。

# B 组 · 效果不对

## 坑 3：delogo 在宽区域会出竖条纹

### 现象

用 ffmpeg 官方的 `delogo` 去字幕，结果是：

```
▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏
```

**规则竖向条纹，比原字幕还难看。**

### 误判

`delogo` 是官方去水印滤镜，**直觉上应该是最佳选择**。
我第一版代码就是用它写的，没做对比测试。

### 真相

`delogo` 靠**区域四周的边缘像素插值**填充：

```
    ↑ 上边缘
  ← [ 字幕区 ] →     ← 左右边缘
    ↓ 下边缘
```

窄条（台标，几十像素）上四周颜色接近，插值自然。
但字幕带 **691 像素宽**，左右采样点跨度太大 → 渐变条纹。

### 修复

改用「降采样 + 放大」做超强模糊。

### 迁移价值

> **官方滤镜 ≠ 适合你的场景。必须用真实素材试。**

## 坑 4：boxblur 的色度半径上限只有 13

### 现象

```bash
boxblur=16:1
```

报错：

```
Invalid chroma_param radius value 16, must be >= 0 and <= 13
```

### 误判

文档和很多博客都说上限是 18。**我信了，直接用了 16。**

### 真相

**色度（chroma）参数的上限是 13**，不是 18。
18 可能是亮度参数的上限，两个不一样。

改成 13 能跑了，但：

```
13 像素的模糊半径扛不住粗体大白字，字迹依然可读
```

### 修复

不用 boxblur，改用 `scale` 降采样。**等效半径由你决定，没有上限。**

### 迁移价值

> **报错信息里的数字最可信，文档和博客都可能过时。**

## 坑 5：字幕检测取了"最长"而不是"最下方"

### 现象

自动检测字幕位置，5 个视频有 2 个检测到了画面中间（猫脸位置）。

### 误判

一开始以为是阈值问题，调了半天阈值。

### 真相

我把规则定成"取**最长**的密集条带"，因为直觉上字幕应该是显著特征。

实测：

```
视频 1（白猫）：猫脸高光区 长度 100，字幕带 长度 68
                → 选了猫脸 ❌
```

**白猫的毛发高光，在灰度上和白色文字无法区分。**

### 修复

改成"取**最靠下**的条带"——因为**台词字幕几乎总在画面下方**。
这个先验比"谁更长"可靠得多。

### 迁移价值

> **当特征本身不可靠时，用"位置/时序"这类结构先验更稳。**

## 坑 6：固定阈值在亮背景上失效

### 现象

字幕检测用固定阈值 235（找白字），结果：

| 素材 | 结果 |
|---|---|
| 暗色室内 | 检不出 |
| 蓝天背景 | **误判**（天空很亮） |
| 白色衣服 | **误判** |

### 真相

**同一个绝对阈值无法适应不同亮度的画面。**

### 修复

自适应阈值——取该帧**最亮的 3%** 作为阈值：

```python
for v in range(255, -1, -1):
    acc += hist[v]
    if acc >= total * 0.03:
        threshold = max(150, v)
        break
```

# C 组 · 静默失效

## 坑 7：心跳不停，状态栏永远"处理中"

### 现象

用户反馈（附截图）：

> "我应该已经执行完成了，可是状态栏还是一直在提示处理"

截图显示：
- 队列 3 个文件**全部绿色已完成**
- 状态栏还停在 "1/3 · 已用 47:39"
- 日志 **732 条**，全是"导出字幕文件…"

### 误判

**一开始以为这是两个问题**：状态栏 bug + 日志刷屏 bug。
分别查了两个方向。

### 真相

```bash
$ grep file_done subgen/*.py
subgen/reporter.py:70:    def file_done(...): ...
subgen/reporter.py:129:   def file_done(...): ...
subgen/reporter.py:244:   def file_done(...): ...
```

**`file_done()` 只在定义，从未被调用！**

因果链：

```
file_done() 没调用
  → 心跳线程不知道任务结束了
  → 继续每秒推 stage="export"
  → ① 覆盖 onJobDone 写的"全部完成"
  → ② 反复触发前端阶段日志
```

**两个看似无关的现象，同一个根因。**

### 修复

三层防护：

1. 正确调用 `file_done()`（成功/失败/取消三条路径）
2. `finally` 兜底调 `finish()`
3. 心跳自身检查 `stage in ("done","error")` 就退出

### 迁移价值

> **两个同时出现的 bug，先找它们的共同根因，别分开查。**
> 分开查会浪费一倍时间。

## 坑 8：已用时间的基准是模块加载时刻

### 现象

状态栏显示"已用 **47:39**"，但任务只跑了几分钟。

### 真相

```python
_T0 = time.time()      # 模块被 import 的时刻！

class CallbackReporter:
    def stage(self, ...):
        self._p.elapsed = self._stage_t0 - _T0    # ← 减的是模块加载时刻
```

**"已用时间" = 程序启动至今。**

用户开着界面 47 分钟才点开始，第一次任务就显示 47:39。

### 修复

```python
def __init__(self, ...):
    self._t0 = time.time()      # 每个实例自己记
```

### 迁移价值

> **模块级的时间戳几乎总是错的。**
> 计时基准应该由使用者在恰当的时候设置。

## 坑 9：模型别名没解析，误下载 3 GB

### 现象

测试时发现程序在下载一个**完全没预期的模型**
（`mobiuslabsgmbh/faster-whisper-large-v3-turbo`）。

### 真相

```python
# ❌ opts.model 是别名 "turbo"
topts = TranscribeOptions(model=opts.model, ...)
```

直接传给 faster-whisper，它把 `"turbo"` 当成 **HuggingFace 仓库名**去联网找。

**于是触发了一次错误的 3 GB 下载。**

### 修复

```python
from .models import resolve_model as _resolve
topts = TranscribeOptions(model=_resolve(opts.model), ...)
```

### 迁移价值

> **别名/简称在系统边界处必须归一化。**
> 内部传别名没问题，但交给外部库前一定要翻译成它认识的形式。

# D 组 · 排查陷阱

这一组最特殊——**问题不在代码，在排查方法本身**。

## 坑 10：测试数据污染，把产物当成了源文件

### 现象

反复测试后，产出文件名变成 `xxx.clean.clean.mp4`，
字幕文件变成 `xxx.clean.srt`。

### 误判

第一反应是"去字幕的输出路径有 bug"，
查了 `default_output` 的逻辑半天。

### 真相

测试脚本这样取源文件：

```python
V = sorted(glob.glob(os.path.join(D, "*.mp4")))[0]
```

而上一轮测试留下的 `xxx.clean.mp4`，
在 `sorted()` 里**排在 `xxx.mp4` 前面**（因为 `.` 的 ASCII 小于 `m`）。

**于是我的测试把上一次的产物当成了源文件。**

### 修复

- 测试脚本固定指定源文件，不用 `sorted()[0]`
- 每轮测试后清理产物

**产品代码其实没问题。** 查了半天是因为看错了地方。

### 迁移价值

> **测试数据要隔离。** 输入和输出不能放在同一个目录里用通配符取。

## 坑 11：测试脚本自己坏了，却以为产品回归了

### 现象

刚修完 WebView2 缓存问题（坑 12），加了回归测试。
第二天测试报错：

```
FAIL  渲染出的是最新版
```

**第一反应：缓存问题又回来了？**

### 真相

单独写调试脚本验证：

```python
r = win.evaluate_js("document.readyState")
# r == 'complete'
r = win.evaluate_js("!!document.querySelector('#sProvider')")
# r == True        ← 产品完全正常！
```

问题在测试脚本本身，两个 bug：

**① 固定 `sleep(4)` 不够稳**——机器忙时页面还没加载完，`evaluate_js` 返回 `None`
**② JS 拼接少了逗号**：

```python
# ❌ 少了逗号分隔
"JSON.stringify({" + ",".join(props) + ", __len: ...})"
# → 生成非法 JSON → json.loads 失败 → 空结果
```

### 修复

- 改成**轮询等待** `document.readyState === 'complete'`
- 用列表 `join` 拼接，不手拼分隔符

### 迁移价值

> **测试报错时，先确认是产品问题还是测试问题。**
> 别急着改产品——可能越改越乱。

## 坑 12：WebView2 强缓存，改了界面看不到

### 现象

用户主动反馈：

> "通过启动界面.bat启动的GUI不是最新的？还需要编译吗"

看到的是几天前的旧界面。

### 排查过程（这个坑的价值在方法）

**第一步：确认要不要编译**

```bash
cat 启动界面.bat
# start "" ".venv\Scripts\pythonw.exe" -m subgen.gui_main
```

**直接跑源码。不需要编译。**

**第二步：确认磁盘文件是新的**

```python
len(open("webui/index.html").read())    # 73550
"sProvider" in html                      # True
```

**磁盘是新的。**

**第三步（关键）：真实启动，回读渲染后的 DOM**

```python
win = webview.create_window("probe", HTML_FILE, js_api=api)
time.sleep(4)
win.evaluate_js("!!document.querySelector('#sProvider')")
# False      ← 渲染出来的是旧版！
```

**磁盘 73550 字符，渲染 66235 字符。**

**第四步：对比启动参数**

| 参数 | 结果 |
|---|---|
| `private_mode=False`（当时用的） | ❌ 旧版 |
| `private_mode=True` | ✅ 新版 |
| `http_server=False` | ✅ 新版 |

**第五步：决定性对照**

同一份文件，只改 URL：

```
不带版本号      → {sProvider: false}   ❌
带 ?v=修改时间  → {sProvider: true}    ✅
```

**根因：WebView2 按 URL 强缓存，无视 no-cache 头，永不过期。**

### 修复

```python
def versioned_url(path):
    return f"{path}?v={int(os.path.getmtime(path))}"
```

### 迁移价值

> **"改了没生效"这类问题，必须用「运行时回读状态」验证，不能只看磁盘文件。**
>
> 磁盘是新的 ≠ 运行时是新的。

# 三条跨坑的通用经验

看完 12 个坑，有几条反复出现的规律：

## 经验一：先问"是产品问题还是测试问题"

坑 11 就是典型。测试失败时，**先花 5 分钟单独验证产品**，
别直接改产品代码。

**方法**：写一个最小复现脚本，绕过测试框架，直接调产品函数。

## 经验二：静默失效最难查，要给"自愈"机制

坑 7、9 都是静默失效——不报错，但行为不对。

**对策**：
- 关键状态转换要有**兜底**（`finally` 里停心跳）
- 机制自身要有**自检**（心跳发现自己该停了就停）
- 不要用异常做流程控制（坑 9 的 `available()` 就是为此而生）

## 经验三：官方/直觉 ≠ 适合你的场景

坑 1（int8）、坑 3（delogo）都是"看起来应该这样，实测不是"。

**对策**：
- 用**真实素材**验证，不用合成的测试数据
- 对比测试至少试 3 个方案，别试一个就下结论
- 记录**实测数据**（数字）而不是"感觉还行"

## 小结

**三句话**：

1. **两个同时出现的 bug，先找共同根因**（坑 7）
2. **测试失败先验证产品**，5 分钟能省 5 小时（坑 11）
3. **"改了没生效"要用运行时回读验证**，磁盘新 ≠ 运行新（坑 12）
